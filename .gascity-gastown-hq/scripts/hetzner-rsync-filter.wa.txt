# COMO É LIDO: o mbp-run.sh passa este arquivo ao rsync como `--filter=". <este arquivo>"`, com --delete --delete-excluded. O rsync usa a PRIMEIRA regra que casa, de cima para baixo —
#   por isso a ORDEM é a segurança: a seção 1 vem antes de `+ /tests/***`, então nada dela sai nem de dentro de tests/. --delete-excluded faz o destino PERDER o que o filtro exclui.
#   Arquivo ausente, ilegível ou fora do formato que o mbp-run.sh confere (filter_sane) = o nó NÃO é usado (estado inerte; cai no MBP).
# O QUE GARANTE (por NOME e PASTA): (1) nome de segredo ou de dado conhecido não sai; (2) nome DESCONHECIDO não sai — fora de tests/ só sai código (py sh js mjs cjs ts css) e os arquivos de
#   dado/config das linhas `+` da seção 3b, cada uma por caminho. .json/.md/.html/.yaml/.sql/.plist com nome neutro em qualquer outra pasta (docs/, scripts/, analysis/, a raiz...) é inerte até
#   alguém listá-lo. Custo de negar demais: teste vermelho no nó, refeito local pelo gate. Nomes de PASTA (só o nome) saem junto com a árvore.
# O QUE NÃO GARANTE: o filtro nunca lê CONTEÚDO. Código com lista de telefones colada (scripts/generate_draft_experiments.py, scripts/draft_comparison_server.py: ~40 e ~20 números) e fixture de
#   tests/ com dump de leads passariam por nome. Quem olha o conteúdo é o mbp-run.sh (node_guard + hetzner-pii-scan.py): retém, no mini, o arquivo com >=20 telefones ou >=3 CPFs distintos, e não
#   usa o nó se não conseguir varrer. É heurística de forma (não vê nome, e-mail, CNPJ nem lista pequena): o resíduo é esse, e vale também para as linhas `+` da seção 3b.
