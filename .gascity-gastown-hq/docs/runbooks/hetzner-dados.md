## Por quê
Os agentes (usuário `runner`) e qualquer dado moram no mesmo usuário do nó. Um pacote npm/PyPI envenenado (ondas Shai-Hulud/CanisterSprawl 2026) ou uma injeção de prompt por página raspada leria o cadastro de lote e proprietário. A decisão do Athos (11/11, programa ga-qg1dw5z) é que esse dado só vai ao nó depois das 3 travas. Esta é a 1ª: o dado fica num usuário que o `runner` não lê, só existe enquanto o build roda, e o build roda sem rede.

## Contrato (o que a trava 3 confere)
Tudo isto é o que o instalador deixa no nó; `hetzner-dados-install.sh --check` (como root) confere os 20 itens e imprime `GTD-CHECK: <item> ok|FALHOU|nao-consegui`.

| O quê | Valor |
|---|---|
| Usuário | `dados`: senha travada (`passwd -l`), **shell real** (`/bin/bash`), home `/home/dados` 0700, grupo próprio, sem grupos extras; o `runner` **não** está no grupo `dados` |
| Staging | `/srv/gtdados`: **tmpfs dedicado** (linha `# gt-dados` no `/etc/fstab`: `size=8g,mode=0700,uid/gid dados,noexec,nosuid,nodev,nofail`), `in/` (o dado) e `out/` (o resultado), 0700 `dados:dados` |
| Código que roda como `dados` | `/opt/gt-dados/app/bin/<entrypoint>`: árvore de **root**, ninguém mais escreve, sem link para fora; lista em `/etc/gt-dados/entrypoints` |
| Wrapper de build | `/usr/local/sbin/gt-dados-run` (root:root 755) |
| Canal do mini | `/usr/local/sbin/gt-dados-ingest` (root:root 755), a única coisa que a chave do mini faz no usuário `dados` |
| Chave do canal | `/etc/ssh/authorized_keys.d/dados` (**root**:dados 0640): `restrict,command="/usr/local/sbin/gt-dados-ingest" <chave do mini>`; drop-in `/etc/ssh/sshd_config.d/50-gt-dados.conf` (`Match User dados`, sem senha, túnel, agente, X11, tty, rc) |
| sudoers | `/etc/sudoers.d/gt-dados-run`: **uma linha por entrypoint**, `runner ALL=(root) NOPASSWD: /usr/local/sbin/gt-dados-run <entrypoint>`; sem curinga, nunca `(dados) ALL` |
| Varredura | `/usr/local/sbin/gt-dados-sweep` (root:root 755) + `gt-dados-sweep.timer` (04:17 UTC, `Persistent=true`); log em `/var/log/gt-dados-sweep.log` |
| Lock | `/run/gt-dados-run.lock`, **root:root 0600** (criado e ajustado pelo wrapper e pela varredura): com 0644 qualquer usuário local, o `runner` incluso, faria `flock -x` nele, travaria todo build e calaria a varredura |
| Swap | **desligada** (com swap ligada o tmpfs iria a disco: o wrapper e o `--check` recusam) |

Linha do log da varredura (a trava 3 lê a última e a idade dela): `<UTC> gt-dados-sweep: LIMPO removed=N killed=K` · `PULADO dados-vivo=N` · `NAO-CONSEGUI <motivo>`. `NAO-CONSEGUI` nunca significa "limpo".

O que o build enxerga (`gt-dados-run`): netns novo **sem saída** (`lo` aceito, o resto rejeitado com contador), uid/gid `dados` sem grupos extras nem capacidades (`setpriv --no-new-privs`), ambiente limpo (`env -i`), `GT_DADOS_STAGE=/srv/gtdados`, prazo de 2 h. Ao fim apaga `in/`, mata o que sobrou no netns e confere que `in/` ficou vazio (`GTD-WIPE: ok`; senão sai 99). `in/` e `out/` são nomes que **o build controla**: se um deles for link simbólico ou arquivo ao começar, o wrapper recusa (`recusado:stage-dirs`, rc 98) sem tocar em nada, e se o build os trocar durante a rodada o fim dá `GTD-WIPE: falhou` (99) em vez de "ok"; a varredura diária apaga o link. Root nunca dá `chown`/`chmod` em caminho que o build escolhe (`mkdir` + `chown -h`, nunca `install -d`).

## Instalação (precisa de root, uma vez)
Sem comando de root improvisado: o que se instala vem de um commit, pelo instalador versionado `scripts/hetzner-dados-install.sh`. A chave de root do nó é `~/.ssh/hetzner_teste_urblink` (usuário `root`; **a trava 2 vai trocá-la, ver "Ordem com a trava 2"**).
```bash
CITY=/Users/athos/gt/.gascity-gastown-hq; NODE=root@2.31.41.222; KEY=~/.ssh/hetzner_teste_urblink
# 1. chave própria do canal mini -> dados (nunca a de root nem a do runner); sem frase porque o mini a usa sem humano
[ -e ~/.ssh/hetzner_dados_ingest ] || ssh-keygen -t ed25519 -N '' -C 'mini->dados (gt-dados-ingest)' -f ~/.ssh/hetzner_dados_ingest
# 2. os scripts de UM commit (não da árvore de trabalho) para uma pasta de root no nó — e a LISTA BRANCA do código (hetzner-dados-code-allow.txt) na MESMA pasta:
#    o instalador a lê ao lado dele; sem ela, `apply --code-dir` recusa `code-allow-ilegivel` (98), antes de mexer no nó (o selftest do instalador lê ESTA linha do scp)
D=$(mktemp -d); git -C "$CITY/.." archive <sha> .gascity-gastown-hq/scripts | tar -x -C "$D"
S=$D/.gascity-gastown-hq/scripts
ssh -i $KEY $NODE 'install -d -m 0700 /root/gt-dados-src' \
  && scp -i $KEY $S/hetzner-dados-{install,run,ingest,sweep,synth}.sh $S/hetzner-dados-code-allow.txt ~/.ssh/hetzner_dados_ingest.pub $NODE:/root/gt-dados-src/
# 3. instalar (idempotente; --stage-size ajusta o tmpfs; --entrypoint acrescenta builds além do `synth` de prova)
ssh -i $KEY $NODE 'bash /root/gt-dados-src/hetzner-dados-install.sh apply --pubkey-file /root/gt-dados-src/hetzner_dados_ingest.pub'
# 4. conferir, ainda como root: tem de dar rc 0 e 20 linhas `ok`
ssh -i $KEY $NODE 'bash /root/gt-dados-src/hetzner-dados-install.sh --check'
```
O instalador só recarrega o sshd **depois** de `sshd -t` e de `sshd -T -C` provarem que o `dados` usa o arquivo de chaves de root e que o `runner` **não** foi afetado; se qualquer prova falha, o drop-in é desfeito e nada é recarregado. O sudoers só entra depois de `visudo -cf`. O fstab ilegível não é reescrito. Um passo que falha imprime `GTD-INSTALL: falhou:<passo>` e sai 98; o que já estava no nó não é apagado (exceto o drop-in reprovado).

Código de build real (a leva 2): o caminho do nó real é `--code-tar <tar> --code-manifest <manifesto> --code-sha <sha>`, exportado no mini (seção «Código do build: exportar no mini, verificar no nó», abaixo). O `--code-dir <repo no nó> --code-sha <sha>` é **LEGADO**: segue aceito, mas AVISA no stderr, porque exige NO NÓ um clone com TODOS os blobs do commit (dado de lead incluso) e só entra com o HEAD igual ao sha **e** árvore limpa. Nos dois caminhos o que vai para a árvore de root é **só o fechamento dos entrypoints pedidos, do conteúdo do commit** (no legado, `git archive <sha> -- <caminhos da lista branca>` do clone do nó; no tar, o tar que o mini exportou; extraído numa pasta nova, dono root, sem escrita de grupo/outros, e trocado de uma vez; falhou → a árvore antiga fica e o instalador sai 98 `code-archive`/`code-modo-inseguro`), nunca o commit inteiro nem o da árvore de trabalho: arquivo ignorado pelo `.gitignore` e edição escondida por `update-index --assume-unchanged` não aparecem em `git status` e não entram; depois `--entrypoint <nome>` para cada executável em `bin/`. Reaplicar com a lista nova **substitui** o sudoers e a lista (uma linha por entrypoint).

**Lista branca do código (wa-4p38ls, P0: o nó não recebe dado de lead/conversa).** O commit do rig tem dado (`hawkey_outbound_messages_48h.csv`, `contacts_auth/`, `docs/investigations/`...) e o `git archive` do commit inteiro o levava ao nó. Agora o apply só exporta os caminhos de `scripts/hetzner-dados-code-allow.txt` (versionada e revisada neste repo; no nó fica **ao lado do instalador**, em `/root/gt-dados-src`, entregue pelo `scp` do passo 2 — nunca um manifesto dentro do commit exportado, que se autorizaria sozinho), no formato `<entrypoint> <caminho>`, um arquivo por linha. Recusa com 98 (as da lista, **antes de mexer no nó**; as do export, sem trocar nada — a árvore antiga fica): `code-allow-ilegivel` (lista ausente/ilegível: nunca "sem lista = exporta tudo"; o motivo mais provável é a lista não ter ido no `scp` do passo 2, e a mensagem diz o caminho que faltou), `code-allow-linha-invalida:<ep>` (glob, `..`, `/` no fim, campo a mais; um nome de pasta sem `/` passa aqui e cai em `code-fora-da-lista`), `code-allow-sem-linha:<ep>` (entrypoint sem linha na lista), `code-allow-sem-bin:<ep>` (entrypoint com linhas, mas sem a do próprio `bin/<ep>`: o instalador só o notaria depois da troca), `code-allow-vazia` (`--code-dir` sem entrypoint de código), `code-archive` (arquivo da lista que não está no commit), `code-fora-da-lista` (o que saiu do archive difere da lista) e `code-dado-no-export:<arquivo>` (arquivo exportado casa `*.csv *.db *.sqlite *.sqlite3 *.jsonl *.parquet *.duckdb *.xlsx *.xls *.vcf`, `contacts_auth/` ou `docs/investigations/`, sem isenção). A isenção é por arquivo e explícita: `@fixture <caminho>` na lista, só para fixture 100 % fictícia. **Entrypoint novo, ou import novo no lado do nó (`main_no`), exige linha nova na lista** (revisada neste repo) — o fechamento é o do caminho do nó, não o import estático do módulo (que inclui imports preguiçosos que só o mini executa): monte uma árvore só com os arquivos da lista e rode `python3 -I <modulo>.py no --stage <pasta vazia>`; tem de falhar por falta do pedido, nunca por `ImportError`. Lista atual: `lotes-tiles` (bin + `lotes_tiles_no.py`), `lotes-adjacencia` (bin + `lot_adjacency_no.py`, `build_lot_adjacency.py`, `lib/dados_no.py`), `spe-alert-build` (bin + `spe_alert_dados.py`, `build_lot_ficha_extra.py`, `lot_ficha_extra_helpers.py`, `lib/{lot_key,drive_materialize,gdrive_reader,shared_data_path}.py`). Os wrappers do rig (`scripts/hetzner_dados_{tiles,lotes,spe}_instala.sh`) não entregam nada: rodam o instalador no lugar (`--install-script`) e passam `--code-dir/--code-sha/--entrypoint` até migrarem para `--code-tar/--code-manifest/--code-sha` (seção «Código do build», abaixo: o `verify-code` substitui os `git -C` que eles fazem no clone), então o `--install-script` tem de apontar para `/root/gt-dados-src/hetzner-dados-install.sh` (a pasta que já leva a lista); apontado para uma pasta sem `hetzner-dados-code-allow.txt` ao lado, o apply recusa `code-allow-ilegivel` sem tocar no nó.

## Código do build: exportar no mini, verificar no nó
O código dos entrypoints chega ao nó como **tar + manifesto exportados no mini**, e o nó só os **verifica**: sem repo e sem nenhum blob de dado (ga-kwk6fcl). O `apply --code-dir` antigo roda `git archive` NO NÓ, e o `git archive` pede ao repo TODO blob do commit: medido no nó (git 2.43), um `git archive <sha> -- <2 arquivos>` num clone parcial com só esses 2 blobs buscou os **8 blobs do commit**, `hawkey_outbound_messages_48h.csv`, `contacts_auth/` e `docs/investigations/` incluídos (e quando o promisor nega o blob o archive falha `code-archive`). Um clone com todos os blobs no nó é exatamente o que a wa-4p38ls proíbe.

```bash
# no MINI, com o repo do rig em dia (`git fetch origin main`): sai code.tar + code.manifest só da lista branca, do COMMIT, já conferidos
bash $CITY/scripts/hetzner-dados-code-export.sh --repo /Users/athos/gt/whatsapp_automation --sha <sha de 40 hex que está em main> \
  --entrypoint lotes-tiles --entrypoint lotes-adjacencia --entrypoint spe-alert-build --out "$HOME/gt-dados-export/<sha12>"
X="$HOME/gt-dados-export/<sha12>"
scp -i $KEY $X/code.tar $X/code.manifest $NODE:/root/gt-dados-src/
# no NÓ, como root (direto, até os wrappers do rig migrarem para --code-tar): o MESMO sha e os MESMOS entrypoints (o apply REESCREVE a lista de entrypoints)
bash /root/gt-dados-src/hetzner-dados-install.sh apply --pubkey-file /root/gt-dados-src/hetzner_dados_ingest.pub \
  --code-tar /root/gt-dados-src/code.tar --code-manifest /root/gt-dados-src/code.manifest --code-sha <sha> \
  --entrypoint lotes-tiles --entrypoint lotes-adjacencia --entrypoint spe-alert-build
```
**O tar é do conjunto INTEIRO de entrypoints do apply.** O `apply` reescreve `/opt/gt-dados/app` e a lista de entrypoints (`/etc/gt-dados/entrypoints`) com o que recebe, então ao instalar um entrypoint novo exporte de novo com os já instalados (`cat /etc/gt-dados/entrypoints` no nó) MAIS o novo. Os wrappers do rig já passam a lista assim (cada um os existentes + o seu), e é a causa comum de `code-manifesto-fora-da-lista:<caminho>`: o caminho nomeado é de um entrypoint que o export não incluiu.

**Manifesto** (`code.manifest`, texto): `gt-dados-code-manifest 1`, `commit <sha>` e uma linha `<modo 100644|100755> <blob-id> <caminho>` por arquivo, que é o `git ls-tree -r <sha>` dos caminhos da lista branca. O blob-id é a identidade do arquivo no git (`git hash-object`): o nó confere cada arquivo contra ele sem precisar do repo.

**O exportador** (`scripts/hetzner-dados-code-export.sh`, só no mini) confere tudo ANTES de qualquer byte sair, e a pasta `--out` (que ele cria, nova: destino que já existe é recusado e nunca tocado) é apagada em qualquer recusa. Recusa 98 `GTD-EXPORT: falhou:<passo>`: `sha-invalido` (só o id de 40 hex minúsculos: nome de ref, abreviação e maiúsculas não valem) · `repo-ilegivel` · `sha-nao-e-commit` (não existe, ou é o id de uma tag) · `sha-fora-de-main` (não é ancestral de `--main-ref`, padrão `origin/main`: é a conferência de que «o sha está em main»; com o ref velho recusa por segurança, faça `git fetch origin main`) · `main-ilegivel` (ref inexistente ou repo que não respondeu: «não consegui saber» nunca vira «está em main») · `code-allow-ilegivel` · `entrypoint-sem-linha:<ep>` e `entrypoint-vazio` (um `git archive` sem caminho levaria o commit INTEIRO) · `out-ja-existe` · `out-nao-criou` · `archive` (arquivo da lista que o commit não tem) · `verify-code` (o motivo exato do instalador vem antes, no stderr) · `mv`. Uso errado sai 64.

**`verify-code`** (`hetzner-dados-install.sh verify-code --code-tar T --code-manifest M --code-sha S [--entrypoint <nome>]...`) é a conferência do `apply` sem o `apply`: roda como qualquer usuário, numa pasta temporária que some em QUALQUER saída, e não toca no nó. O exportador a roda no que exportou, então dado na lista e pasta na lista reprovam no mini, e o archive é da ÁRVORE do commit (`<sha>^{tree}`: sem o cabeçalho global PAX, que cada `tar` trata a seu modo, e sem expandir `export-subst`, medido no git 2.43). Um `.gitattributes` que ainda **converte** o arquivo no archive (`eol`, `filter`: `code-hash:<arquivo>`) ou o **omite** (`export-ignore`: `code-fora-da-lista`) reprova no mini: conserte o atributo, não a lista. O wrapper do rig também pode rodá-la no nó antes do pip, para falhar cedo (ela substitui os `git -C <clone> rev-parse/status/ls-files` dos wrappers: sha, árvore limpa e `bin/<ep>` executável no commit).

**O que o `apply` do nó recusa** (98 `GTD-INSTALL: falhou:<código>`; sem trocar a árvore antiga):
- **antes de mexer no nó e antes de extrair** (nenhum byte do tar é gravado): `code-sha-invalido` · `code-tar-ilegivel` (ausente, pasta, FIFO, ou o `tar -t` não lê) · `code-manifesto-ilegivel` · `code-manifesto-vazio` · `code-manifesto-invalido:<n>` (a linha n não casa o formato, 1 é o cabeçalho; modo que não é 100644/100755, blob-id que não é 40 hex minúsculos, caminho com `..`/`/` no fim, tabulação, CRLF) · `code-manifesto-commit-diferente` (o commit do manifesto não é o `--code-sha`) · `code-manifesto-fora-da-lista:<1º caminho que difere>` (o conjunto do manifesto, linha duplicada incluída, difere do que a lista branca autoriza para os entrypoints pedidos: quase sempre um export com MENOS entrypoints que o apply, veja acima) · `code-bin-sem-exec:<ep>` (`bin/<ep>` não é 100755 NO COMMIT) · `code-tar-vazio` · `code-tar-tipo:<c>` (membro que não é arquivo nem pasta: `l` elo simbólico, `h` elo duro...) · `code-tar-nome:<nome>` (nome absoluto, `..`, `./`: só o layout do `git archive` vale) · `code-tar-fora-do-manifesto:<nome>` (o que o manifesto não lista, o csv de lead por exemplo, nem chega a ser gravado no nó) · e os da lista branca (`code-allow-*`);
- **na extração** (numa pasta nova de root, a árvore antiga fica): `code-tar-extracao` · `code-fora-da-lista` · `code-dado-no-export:<arquivo>` · `code-modo-inseguro:<caminho>` · `code-elo-no-export:<arquivo>` · `code-hash:<arquivo>` (o blob-id do arquivo extraído, calculado com `git hash-object --no-filters` para o `core.autocrlf` do git do operador não converter nada, difere do manifesto) · `code-modo-difere:<arquivo>` (o bit de execução do arquivo difere do modo do manifesto).

No nó o git só roda `hash-object`, sem repositório: o selftest prova isso com um `git` que sai 97 em qualquer outro subcomando.

## Prova (como runner)
No nó, como `runner` (sem root): `bash <repo>/scripts/hetzner-dados-prove.sh`, ou do mini `ssh hetzner-teste 'bash -s' < scripts/hetzner-dados-prove.sh`. Imprime `GTD-PROVE: <item> ok|FALHOU|nao-consegui` e `GTD-PROVE: resultado ...` (rc 0 todos ok · 1 algum FALHOU · 2 algum nao-consegui):

| Item | ok quando |
|---|---|
| `home-negado`, `stage-negado` | `ls /home/dados` e `ls /srv/gtdados/in` dão **Permission denied** (diretório que não existe = `nao-consegui`: trava não instalada, nunca ok) |
| `sem-grupo-dados` | `id -nG` não lista `dados` |
| `sudo-como-dados-recusado` | `sudo -n -u dados true` recusa |
| `fora-da-lista-recusado` | `sudo -n gt-dados-run <nome fora da lista>` recusa e não roda nada |
| `build-sintetico` | `sudo -n gt-dados-run synth` sai 0, imprime `synth: ok files=5` (a contagem do que existe em `in/synth`), `GTD-WIPE: ok` e `GTD-EGRESS: attempts=<n>` com **n ≥ 1** (`attempts=0` = a sonda de rede nunca chegou ao netns: `FALHOU`, isolamento não provado); o dado é **sintético**, gerado na hora (nunca dado real) |

A conferência do staging **vazio** depois do build é de root: a linha `GTD-WIPE: ok` do wrapper (ele lê como root) e o `--check`.

## Como o mini usa (put, run, get)
O mini tem **uma** chave no usuário `dados` (`~/.ssh/hetzner_dados_ingest`), e ela só roda `gt-dados-ingest`. Os verbos vêm em `SSH_ORIGINAL_COMMAND`; o nome casa `^[a-z0-9][a-z0-9_.-]{0,63}$`:
```bash
tar -c -C <pasta> . | ssh -i ~/.ssh/hetzner_dados_ingest dados@2.31.41.222 put <nome>     # dado -> /srv/gtdados/in/<nome>/ (link simbólico no tar: apagado e rc 65)
ssh hetzner-teste 'sudo -n /usr/local/sbin/gt-dados-run <entrypoint>'                         # build (runner dispara; só entrypoint da lista)
ssh -i ~/.ssh/hetzner_dados_ingest dados@2.31.41.222 get <nome> | tar -x -C <destino>        # resultado -> mini (ausente ou sem arquivo regular: rc 66, nunca tar vazio)
ssh -i ~/.ssh/hetzner_dados_ingest dados@2.31.41.222 clean [<nome>]                          # apaga in/ e out/
ssh -i ~/.ssh/hetzner_dados_ingest dados@2.31.41.222 status                                  # tmpfs sim/não e itens em in/ e out/
```
Códigos do ingest: 0 ok · 64 verbo/nome recusado · 65 link simbólico · 66 resultado ausente ou sem nenhum arquivo regular · 67 `put` sem arquivo nenhum (o tar do remetente morreu e deixou um arquivo válido e vazio: apagado, nunca "ok files=0") · 73 não consegui criar o destino · 74 `status` que não conseguiu contar (`in=?`) ou `get` que não conseguiu ler · 98 o staging não é tmpfs próprio, ou `in/`/`out/` não é diretório de verdade (o dado **não** é gravado) · 99 apaguei mas sobrou. `in/` e `out/` são nomes que o build (`dados`) controla: se ele os trocar por link simbólico ou arquivo, `put`, `get` e `clean <nome>` recusam `stage-dirs` (98; um caminho pelo link gravaria o dado fora do tmpfs, em disco), `status` conta `?` (rc 74) e `clean` sem nome apaga o próprio link. O resultado nunca sai por diretório legível ao `runner`.

## Varredura e log
O trap do wrapper cobre saída normal, `INT`, `TERM`, `HUP`; `kill -9` e reboot o pulam. A varredura diária apaga o staging, o home do `dados` e o que `dados` deixou em `/tmp`, `/var/tmp` e `/dev/shm`, **se não houver build vivo**: nenhum processo de `dados` com menos de 3 h **e** o lock do wrapper (`/run/gt-dados-run.lock`) livre. Processo de `dados` com 3 h ou mais não é build (o prazo do wrapper é 2 h): é morto e a varredura segue, mas só quando não há processo jovem de `dados` (com um, a varredura inteira é `PULADO` e nada é morto: o velho fica para o dia seguinte). Se a linha não puder ser gravada no log, o resultado é `NAO-CONSEGUI escrever <log>` (rc 2), nunca `LIMPO`. A varredura **segura o lock até o fim**: um build que comece no meio recusa `ocupado` (`GTD-RUN: recusado:ocupado`, rc 98) em vez de ter o staging apagado. O lock é só de root (0600). Tomado depois da espera de 10 s **e** com processo de `dados` vivo → `PULADO build-vivo lock=ocupado dados=N`; tomado **sem** processo de `dados` (preso por outra coisa) → `NAO-CONSEGUI lock-tomado-sem-build`, nunca "build vivo". A leitura de processos passa por `awk`: `awk` que falha ou entrega algo que não é número (contagem de vivos, pid de velho, contagem da 2ª leitura) é `NAO-CONSEGUI awk-falhou|live-ilegivel|old-ilegivel|l2-ilegivel` (rc 2, nada apagado), nunca "0 processos vivos". Se a contagem de itens apagados não puder ser lida mas a conferência de que sumiu passou, a linha `LIMPO` termina em `contagem=incompleta` (nunca um `removed=0` que pareça "nada havia"). Roda uma vez na instalação, **com prazo de 15 min**: se estourar ou sair `NAO-CONSEGUI`, a instalação falha (`GTD-INSTALL: falhou:sweep-primeira`, rc 98).

Alcance em `/tmp`: só o **1º nível** (o que `dados` cria direto lá, com o que houver dentro). O `/tmp` do nó tem ~1,7 milhão de entradas (medido em 12/11: 17,8 mi de inodes no `/`); a primeira versão varria a árvore inteira, ficou 40+ min presa e **nunca escreveu o log**. `/var/tmp` e `/dev/shm` são varridos inteiros. Cada apagamento e cada leitura de verificação tem prazo de 15 min: a verificação que estourou = `NAO-CONSEGUI leitura-falhou`. Entrada que **sumiu** durante a leitura (`No such file or directory`: o `runner` apaga e cria em `/tmp` o tempo todo) não reprova; qualquer outro erro de leitura reprova.

Ler: `tail -3 /var/log/gt-dados-sweep.log` ou `journalctl -u gt-dados-sweep`. Rodar à mão: `systemctl start gt-dados-sweep.service` (medido no nó em 12/11: 13 a 37 s, conforme o cache de disco). **Trava 3:** `PULADO` em duas varreduras seguidas (mais de 24 h sem `LIMPO`) é anomalia (o prazo do wrapper é 2 h), investigar. Uma varredura **sem linha no log** (serviço `activating` por mais de ~15 min) é defeito, não "limpo".

## Ordem com a trava 2
A trava 2 (ga-qg1dw5z.2) troca a chave de root e a descreve como "não lida por agentes": depois dela nenhum dog aplica root no nó, só o Athos. Por isso:
1. **Aplicar a trava 1 ANTES de a 2 cortar o root.** Se a 2 já cortou, a instalação (e qualquer mudança de entrypoint) é do Athos, com este mesmo instalador.
2. A `ufw` da trava 2 precisa deixar o ssh do mini entrar também como `dados` (mesma origem do `runner`).
3. A trava 2 não pode mexer no `AuthorizedKeysFile` do `Match User dados`: se mudar o sshd globalmente, rode `hetzner-dados-install.sh --check` (`sshd-dados-usa-arquivo-de-root`, `sshd-runner-intacto`).

## Limites honestos
- **Os selftests usam stubs** (`hetzner-dados.selftest.sh`: wrapper, ingest, varredura, synth e prove, 242 casos e 57 mutantes; `hetzner-dados-install.selftest.sh`: instalador, 192 casos e 63 mutantes, numa "raiz" de mentira; um caso monta a pasta do nó só com o que o `scp` do passo 2 entrega, lido deste runbook; `hetzner-dados-install-tar.selftest.sh`: o ramo do tar e o `verify-code` do instalador, 176 itens entre casos e mutantes; `hetzner-dados-code-export.selftest.sh`: o exportador do mini com repos git de verdade, 73 itens) e **não veem o tamanho do nó**: a varredura passou nos selftests e travou 40+ min no `/tmp` real (1,7 mi de entradas). A prova de que o kernel isola, de que o sshd aceita a chave, de que o sudo recusa e de que a varredura termina é o `--check`, o `hetzner-dados-prove.sh` e a 1ª varredura da instalação **no nó**, depois da instalação por root (feitos em 12/11, ver o comentário da bead ga-joysgpf).
- **`/tmp` só no 1º nível e `put` concorrente**: arquivo de `dados` dentro de pasta de OUTRO dono em `/tmp` não é visto pela varredura; e um `put` do canal do mini que comece depois da checagem de processos da varredura (o `ingest` não toma o lock) não é protegido: não rode `put` por volta de 04:17 UTC. Um build legítimo não deve gravar em `/tmp` (o wrapper não define `TMPDIR`; temporário do build iria ao disco, não ao tmpfs): lacuna conhecida, a tratar quando o 1º build real da leva 2 existir.
- **"Sem rede" é um netns**, o mesmo padrão do `gt-netns-run`: soquete unix do sistema de arquivos (D-Bus, `docker.sock`) não é coberto. O `dados` não tem home legível pelo `runner`, mas um build envenenado **roda como `dados`** e lê o que está no staging dele: a trava protege o dado do `runner` e do que ele instala, não de um entrypoint malicioso dentro da árvore de root (por isso a árvore é de root e é o conteúdo do commit fixado por sha, extraído com `git archive`: arquivo ignorado ou edição não commitada na árvore de trabalho não entra).
- **Tmpfs usa RAM** (`--stage-size`, padrão 8g; o nó tem 30 GB, sem swap). Dado maior que o tmpfs falha o `put` (ENOSPC), não vai ao disco. A trava 3 deve acusar **swap ligada** enquanto houver dado.
- Reboot apaga o staging (é tmpfs); `shred` em ext4/SSD não garantiria, por isso não há staging em bloco de disco.
- O `dados` tem shell real **de propósito**: com `nologin` o `sshd` não roda o `command=` (ele o executa pelo shell do usuário). "Sem login" aqui é senha travada + chave com `restrict,command=` + `PermitTTY no`.
- **O tar e o manifesto valem pelo canal, não por assinatura**: o manifesto liga os bytes de cada arquivo ao blob-id do commit e o instalador recusa qualquer diferença, mas tar e manifesto viajam JUNTOS: quem pudesse trocar os dois escreveria código que roda como `dados`. Por isso os dois só entram vindos do `scp` de root do mini para `/root/gt-dados-src` (0700, como a chave e os scripts), nunca de pasta que o `runner` escreva, e o `--code-sha` é o que o operador conferiu no mini.
- O arquivo de chaves do `dados` é de **root** e não gravável por `dados`: senão um build envenenado gravaria a própria chave e ganharia acesso externo permanente.

Referências: `scripts/hetzner-dados-*.sh` (o que roda), `docs/runbooks/hetzner-nightly-tests.md` e `scripts/hetzner-netns-run.sh` (o padrão do netns e da instalação de root).
