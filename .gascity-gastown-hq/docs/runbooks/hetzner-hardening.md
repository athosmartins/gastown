## O guarda de clone

`scripts/remote-clone-guard.py`, hook PreToolUse em `Bash` e `Edit|Write|MultiEdit|NotebookEdit`, instalado em `~/.claude/hooks/` do servidor pelo `push-bundle` (o `remote-bundle-build.py` o leva e troca a linha `drop` do hook do mini por esta, `swap` na `POLICY`, com `replaced_by` no manifest).

* **Território** = `~/gt-remote/git` (`<repo>/repo.git` = o espelho, `<repo>/wt/<bead>` = um worktree por sessão). **Clone próprio** = o ancestral com `.git` de `$CLAUDE_PROJECT_DIR`; sem a variável não há clone próprio e toda escrita no território é bloqueada.
* **Bloqueia** (exit 2, mensagem diz o alvo, o clone próprio, que não é o usuário cancelando e que leitura segue livre): `git` de escrita (commit/push/merge/rebase/reset/checkout/add/stash/clean/branch -D/fetch/pull…) cujo alvo resolvido cai no território fora do clone próprio, e Edit/Write/MultiEdit/NotebookEdit em arquivo desse tipo de alvo ou em `~/.claude/hooks/**` e `~/.claude/settings*.json` (o guarda não se desliga por engano). **Libera**: leitura em qualquer clone (log/status/diff/show/blame/ls-files…), escrita no próprio clone, escrita fora do território, comando que só *cita* o outro clone (echo, mensagem de commit, heredoc).
* **Três estados**: alvo que não sei resolver numa escrita (`$VAR`, glob, crase, `~usuário`), subcomando desconhecido, `cd`/`pushd` que não sei seguir, exceção do próprio guarda → **bloqueia**. Stdin que não é JSON: **bloqueia se o texto cita `git`, `file_path` ou `notebook_path`** (não dá para conferir um pedido que pode tocar git ou arquivo); se não cita nenhum dos três, **libera** (lixo no stdin não derruba a sessão inteira; o Claude sempre manda JSON válido). O comando do hook é `python3 -I <guarda> || exit 2`, porque hook que sai 1 ou 127 **não** bloqueia (falha aberta); assim travar, sumir o python ou o arquivo também sai 2.
* **Onde o `git` pode estar** (cada forma tem caso no selftest; a regra que cobre a CLASSE está em "Como o guarda decide"): depois de `;` `&&` `||` `|` `( )` `{`, de palavra reservada (`if`/`then`/`else`/`elif`/`do`/`while`/`until`/`!`/`function f {`/`coproc`), de `cd`/`pushd`, de `command`/`env`/`sudo`/`xargs`/`nohup`…, em `bash -c` (também `bash -c -e '…'`: o script é a primeira palavra depois do `-c` que não é opção), `eval`, `$(…)`, crase, `<(…)`/`>(…)`, `find -exec`/`-ok` (inclusive um segundo `-exec` depois do `\;` ou do `';'`), e no corpo de heredoc ou here-string que um shell lê (`bash <<EOF`). `cd`/`pushd` só é seguido com opções `-L`/`-P`/`-e`/`-@`, `--` e **um** argumento; `cd -Z x`, dois argumentos, `pushd +1` e `pushd` sozinho deixam o diretório "não sei" (escrita sem `-C` absoluto bloqueia).
* **Embrulhos e opções que o guarda não lê** (gate ga-iczduy, rodadas 1 e 2 — o MESMO defeito, "o que não entendo vale 'não é git'", em lugares diferentes): cada embrulho (`command`, `env`, `sudo`, `doas`, `xargs`, `nice`, `timeout`, `stdbuf`, `setsid`, `exec`, `time`, `nohup`) tem a tabela das SUAS opções (`WOPT` no guarda; antes era uma tabela só, e `sudo -n git -C <alheio> commit` passava porque o `-n` do `xargs` leva argumento e engolia o `git`). Opção que não está na tabela = não sei onde o comando começa, e o embrulho vale como lançador opaco (abaixo). `find -execdir`/`-okdir` rodam o comando no diretório de **cada achado**, que o guarda não conhece: diretório "não sei" (git de escrita ali só passa com `-C <caminho absoluto>`; leitura passa). Opção de topo do git que leva valor (`--attr-source HEAD`) é pulada; uma que não conheço deixa o diretório "não sei" e vale como escrita (falso positivo assumido: `git --opção-nova VALOR -C <seu clone> commit` bloqueia). O número colado num redirecionamento (`2>/dev/null`) é o descritor, não um argumento (antes `cd <próprio> 2>/dev/null && git commit` bloqueava).
* **Aspas, barra e palavra vazia** (gate ga-cgu53f, rodada 3 — o MESMO defeito: o `shlex` tira as aspas e a barra, e o que o shell lê como texto chegava ao guarda como operador, ou como NADA): `echo '>' && git -C <alheio> commit` (também `\>`, `'<'` + newline, `tr -d '<>' ; git …`), `git -C <alheio> commit -m '>'` (o `>` entre aspas engolia o `;` do fim) e `git -C '' -C <alheio> commit` (a palavra vazia sumia) passavam. Agora cada `;` `&` `|` `(` `)` `<` `>` entre aspas ou depois de `\` é texto (`protect()` troca por um caractere reservado antes do shlex e devolve depois de decidir quem é operador), `$'…'` tem os escapes decodificados e `$"…"` perde o `$`, a palavra vazia fica no lugar, um redirecionamento leva UMA palavra como alvo (e o `$( )` dela roda) e um operador onde devia haver alvo continua sendo operador (`git … >` sem alvo é erro de sintaxe no shell; aqui o trecho é conferido do mesmo jeito). O regex de heredoc não casa mais o segundo `<<` de `<<<`, e o `\;`/`';'`/`'('` do `find` são palavras dele, não separadores. Aspa que não fecha (ou `\` no fim): o shell recusa a linha e só roda o que veio ANTES dela, e aspa, crase ou `\` dentro de um comentário `#` NÃO conta como aspa (gate-fix 8: antes a aspa de `# Don't` pareava com a de um `-m 'msg'` na linha seguinte e engolia o `git` entre elas; `decomment()` as troca por espaço e as palavras do comentário seguem conferidas); a aspa que ainda sobra solta sai do texto e o resto é conferido como comando (uma hipótese só, a do lado fechado) (antes o texto era "separado na marra", sem agrupar as aspas que fecham, e `bash -c 'git -C <alheio> commit' # it's` passava; a versão anterior à rodada 3 tinha o mesmo furo). O texto de um comentário também é conferido como comando (`git status # a; git -C <alheio> commit` bloqueia).
* **Destino por argumento** (mesmo gate, medium): `git worktree remove --force ../outro`, `worktree move`, `clone <repo> <outro>/sub`, `init <outro>/sub`, `checkout-index --prefix=<outro>/`, `archive -o`, `format-patch -o`… escrevem onde o ARGUMENTO manda, sem `-C`, e passavam do clone próprio. Agora em worktree/clone/init/checkout-index/submodule/archive/bundle/format-patch toda palavra conta como caminho (também `--opção=valor` e `-oVALOR`), e em qualquer subcomando o valor de `--output`/`--prefix`/`--separate-git-dir`/`--lost-found`/`--file`/`--template`; URL (`https://…`) não é caminho. Falsos positivos assumidos: `git clone <clone alheio> <seu clone>/sub` e `git submodule add <caminho no alheio> …` bloqueiam (não separo a origem do destino). Destino em opção ou subcomando que a lista não tem (`config -f <arquivo>`, `fast-import --export-marks=…`, `pack-objects <base>`) **não** é conferido.
* **Lançadores que o guarda não modela** (`flock`, `ionice`, `chrt`, `taskset`, `parallel`, `su`, `runuser`, `ssh`, `script`, `trap`, `watch`, `unshare`, `nsenter`, `chroot`, `setpriv`, `numactl`, `strace`, `fakeroot`, `systemd-run`, `busybox`, `dbus-run-session`, `xvfb-run`, `unbuffer`, `caffeinate`, `tmux`, `screen`, `expect`): o guarda abre o comando, mas com o diretório "não sei" — o `git` dentro passa se for leitura ou com `-C <caminho absoluto>`, e bloqueia se for escrita com diretório implícito ou com `$VAR` (falso positivo conhecido: `flock L git commit` bloqueia, e o mesmo vale para um embrulho com opção que não conheço, `sudo --nova git commit`; escreva `git -C <seu clone> commit`). **A lista é fechada**: um lançador fora dela (`lockrun git …`) esconde o git.
* **Leitura que traz configuração capaz de rodar programa deixa de ser leitura** (parecer de segurança do push, rodada 1): `git -C <alheio> -c alias.x='!…' log`, `-c core.pager=…`/`core.fsmonitor=…`, `--config-env`, `-p`/`--paginate`, `--exec-path` e as variáveis `GIT_CONFIG_*`, `GIT_PAGER`, `GIT_EXTERNAL_DIFF`, `GIT_SSH*`, `GIT_ASKPASS`, `GIT_EDITOR`… bloqueiam no clone alheio (a mensagem diz "leitura com configuração que roda programa"). Só chave de exibição ou identidade (`color.*`, `advice.*`, `core.quotepath`/`abbrev`, `safe.directory`, `user.name`/`email`) segue como leitura; chave que não conheço = não sei = escrita. Falso positivo conhecido: `GIT_PAGER=cat git -C <alheio> log` bloqueia (no próprio clone passa). Não vejo a configuração que JÁ está no `.git/config` do clone alheio (alias, filter, textconv, fsmonitor: uma leitura lá a executa).
* **Interpretador e pipe** (ga-tphd15o; achado do ga-nkfwixz, que rodou o cc-safety-net como oráculo diferencial contra o bash real: das 68 formas que o guarda admitia não cobrir, 12 só o oráculo pegava). O texto de shell que chega por um interpretador ou por um pipe é conferido como comando. (1) `python -c`, `node -e`, `perl -e`, `ruby -e` e `awk '…'`: o código inteiro é conferido como texto de shell e cada literal dele também (aspas simples ou duplas, `q{}`/`qq{}`/`qx{}`, `%x{}`), o que cobre `os.system`, `shell=True`, `execSync`, `exec`, `system` com ou sem parêntese, crase e `"cmd" | getline`. Se o código cita `chdir` ou `cwd=`/`cwd:`, o diretório do shell que ele abre vira "não sei" (escrita sem `-C` absoluto bloqueia); a chave `'cwd'` entre aspas de um JSON não conta (o replay de pedidos reais achou um `python -c` que só montava um JSON e bloqueava). (2) Um shell sem `-c` (`sh`, `bash -s`, `zsh`…) ligado por pipe a um texto que o guarda sabe ler é reescrito para `sh -c '<texto>'`; a reescrita é do trecho, então vale também no corpo de função. O texto vem de `echo`/`printf` literais (o formato é reaproveitado como no shell, `echo -e` decodifica os escapes, `$NOME` e `$( )` nos argumentos são lidos como no `eval`) ou de um here-string (`cat <<< '…' | sh`), passando por `cat`/`tee` (repassam), `base64 -d` (`--decode`, `-D`) e `rev`. (3) `eval`: um `$( )` que só imprime texto assim é trocado pelo texto, e `printf -v NOME …`/`NOME=…` guardam o texto (mesmo se o trecho pode não ter rodado: lado fechado) para o `eval "$NOME"` conferir; só a palavra INTEIRA é trocada, nunca um pedaço dela. Falsos positivos assumidos: texto entre aspas passado a um interpretador que PARECE `git <escrita> -C <alheio>` bloqueia mesmo se o programa só o imprimir (como o corpo de heredoc); `{cwd: <próprio>}` deixa o diretório "não sei"; `echo '…' | sh script.sh` conta o texto como programa. **Continua sem ver**: lista de argumentos (`subprocess.run(['git', '-C', d, …])`, `spawnSync`, `Popen([…])`), caminho em variável do código, texto montado em pedaços ou por f-string, script em arquivo, interpretador que lê o programa do stdin, grupo `{ …; }` ou `( … )` como produtor do pipe, `tr`/`xxd`/`openssl` no meio, `$(a; b)`, `bash <(echo '…')`, `xargs sh -c`, `local`/`read` guardando o texto. `ruby` e `base64 -D` só foram conferidos pelo texto (nenhum dos dois roda neste nó Linux). Medido contra o shell real com `git` falso: o corpus de 68 formas (as 12 passam de 0 para 2; as 13 de lista/variável/script seguem abertas; nenhum alvo PRÓPRIO passou a bloquear), o fuzzer da semente 7 com 1500 comandos (1098 escritas no alheio, 0 bypass, nenhuma decisão mudou, 26 de 26 `reset --hard` dentro de `$(case … esac)` seguem bloqueados), um fuzzer das famílias novas (4 sementes × 1000, 0 bypass nas formas pedidas) e 24.170 pedidos Bash REAIS das transcrições deste nó (base × novo, nenhuma decisão real mudou). Custo: +1,4 a +3,4 ms sobre ~55 ms por chamada do hook.
* **O que NÃO cobre** (é trava contra engano, não sandbox): script que o comando executa (`bash x.sh`), `source`, variável que guarda o `git`, lista de argumentos de interpretador (`subprocess.run(['git', …])`) e texto montado em pedaços (ver "Interpretador e pipe"), função ou alias definido em outra chamada, e redirecionamento (`> arquivo`), `cp`, `sed -i`, `rm` no clone alheio ou nos hooks/settings do claude, e Edit/Write em `.claude/settings*.json` da pasta do próprio clone (a camada do projeto só é conferida na abertura da sessão). Também não vejo QUAL ref o git escreve, só ONDE ele roda: do clone próprio, `git push origin --delete worker/<outra sessão>` (ou `:worker/<outra>`, `push --force … HEAD:worker/<outra>`), `branch -D`, `update-ref`, `worktree prune` e `gc --prune=now` mexem no estado COMPARTILHADO (o espelho `repo.git`) sem citar o caminho do alheio; e `$'…'` só tem decodificados `\xHH`, `\NNN`, `\uHHHH`, `\UHHHHHHHH` e os escapes de uma letra. O fecho de verdade é um usuário Unix por sessão: **não está feito nem tem bead**.
* `--selfcheck [settings.json [pasta-do-projeto…]]`: 0 se o guarda decide como deveria numa pasta de teste e, com o settings, todo PreToolUse dos 5 tipos de ferramenta chama **este** arquivo com `|| exit 2`, **sem campo que mude quando o hook dispara** (`if`, `async`…: o hook só pode ter `type`/`command`/`timeout`; o cross-clone-block do mini tinha `"if": "Bash(git -C *)"`) e `disableAllHooks` não está ligado nele nem em `<pasta>/.claude/settings[.local].json` (a camada do projeto também desliga hook; ausente = nada a conferir, ilegível = reprova).
* **`cd` que pode não ter rodado não muda o diretório** (gate da fatia 6a, tentativa 3 — "a variável em que se DECIDE tem de ser a mesma em que se AGE"): `cd a 2>/dev/null || cd b; git …`, `if …; then cd a; else cd b; fi; git …`, `x && cd a; git …` (a cadeia `&&` não segue até o git), `cd a | …`, `cd a &` deixam o diretório **"não sei"** e a escrita bloqueia. Mantêm o diretório só os casos em que o cd COM CERTEZA rodou e o comando seguinte depende dele: `cd a || exit`/`|| return` e `x && cd a && git …` — e, neste último, só ENQUANTO a cadeia `&&` continua: no primeiro `;`/`||`/`&`/newline depois de um cd que não era o 1º da cadeia o diretório vira "não sei" (`cd other; false && cd own && true; git …` bloqueia: o shell ficou em other). Também "não sei": cd num padrão de `case` (`x) cd a;;`), dentro de corpo de função (`f() { cd a; }` — pode nunca rodar, ou rodar depois) e num grupo em background (`{ cd a; } &`). Um `cd` que é o 1º comando da linha/cadeia (`cd a && true; git …`) rodou com certeza e mantém. E **`<<EOF` entre aspas ou escapado é texto** (`git commit -m "doc: cat <<EOF"`): não abre heredoc, as linhas seguintes continuam sendo comandos conferidos (antes, um `EOF` solto linhas abaixo engolia tudo no meio). Grupo `cond` do selftest + 3 mutantes.
* Selftest `scripts/remote-clone-guard.selftest.sh`: **1150 de 1150 no nó Linux** (969 casos + 180 mutantes + o controle do stub, que falha 592 de 860; o grupo `interp` da ga-tphd15o são 114 desses casos e 40 desses mutantes). Falsos positivos medidos pelo fuzzer: ~5% das escritas no PRÓPRIO clone bloqueiam (cd em ramo de case, `command cd`, export em if) — lado fechado. Gate-fix 7: grupo `ctx` e 20 dos 21 repros do gate ga-37bwre liberavam em `b0bb95e36`. Antes: 932 de 932 (807 casos + 125 mutantes, cada um com UMA guarda apagada e o grupo que a cobre reprovando, + o controle contra um stub que só sai 0 — o servidor *antes* desta fatia —, que falha 485 de 692 casos; os 754 casos também passam sob o Python 3.9.6 do sistema). Rodada 3 (ga-cgu53f): os 221 casos novos dos grupos `lex` (147: aspas, `\`, `''`, `$'…'`, alvo de redirecionamento, aspa que não fecha, heredoc/`<<<`/find) e `dest` (74: destino por argumento) foram rodados contra o guarda de `06a68be5a`: **114 reprovam lá**. ## Como o guarda decide

Texto que antes ficava no topo do `remote-clone-guard.py` (saiu de lá para caber no teto E11 do gate; o código aponta para cá).

**Regra.** Três estados — sei que pode / sei que não pode / não sei — e o último NÃO vira "pode". Território = `$RCG_ROOT`, senão `~/gt-remote/git`. Clone próprio = o ancestral com `.git` de `$CLAUDE_PROJECT_DIR` (sem a variável, toda escrita no território bloqueia). Para cada `git` do comando (atrás de `;` `&&` `||` `|` `( )` `{`, de if/then/else/do/while/!/function, cd/pushd, command/env/sudo/xargs…, `bash -c` / `eval` / `$(…)` / crases / `<(…)`, `find -exec`, heredoc ou here-string que um shell lê) o alvo = diretório dos `-C` + `--git-dir`/`--work-tree`/`GIT_DIR`/`GIT_WORK_TREE`, resolvido com realpath; também o destino por ARGUMENTO (worktree/clone/init/checkout-index/submodule/archive/bundle/format-patch: toda palavra; `--output`/`--prefix`/`--file`… em qualquer subcomando). Subcomando fora da lista de LEITURA (alias, desconhecido) = escrita; leitura com configuração que roda programa (`-c alias.*`/`core.pager`…, `-p`, `--exec-path`, `GIT_CONFIG_*`/`GIT_PAGER`/`GIT_SSH*`…; lista fechada) = escrita. Alvo no território fora do clone próprio → bloqueia; alvo que não resolvo (`$VAR`, glob, crase, `~usuário`) numa escrita → bloqueia.

**Um contexto só** (gate da 6a, tentativa 7, ga-37bwre). Todo trecho aninhado — `$( )`, crase, `bash -c`, `eval`, `env -S`, here-string que um shell lê, texto passado a lançador opaco — é conferido com o MESMO contexto do trecho de fora: as variáveis (`GIT_DIR=x bash -c 'git commit'`, `export GIT_DIR=x; eval '…'`, `GIT_DIR=x; echo $(git commit)`) e as funções desta chamada (`f() {…}; echo $(f)`, `eval f`, `export -f f; bash -c f`). Antes, cada `scan()` aninhado começava do zero: a variável em que o guarda decidia não era a em que o shell agia.

**"Não sei"** (e escrita ali bloqueia): cd/pushd com opção/forma que não entendo; cd que pode não ter rodado (depois de `||`, em pipeline/background, em ramo de if/case, no meio de cadeia `&&` que não segue até o git) ou cujo diretório não existe; corpo de função roda no cwd da CHAMADA; **função cujo fim o guarda não acha** (uma `{` entre aspas no corpo desconta a conta de chaves) → o corpo é conferido no fim como se rodasse, em diretório "não sei"; opção de topo do git que não conheço; embrulho com opção fora da tabela WOPT; lançador que não modelo (OPAQUE: flock, ssh, su, tmux…); find -execdir/-okdir.

**Heredoc.** O que o SHELL lê como texto não é operador nem some: pontuação entre aspas/escapada, `$'…'`, `$"…"`, palavra vazia, `<<EOF` entre aspas, em comentário ou em `$(( ))`. Heredoc de verdade vai até a linha que é exatamente o delimitador (sem terminador, nada some). O corpo só é descartado como DADO quando todo comando da linha do `<<` — tirados os redirecionamentos (`sh<<EOF`, `<<EOF bash`, `0<<EOF sh`, `2>/dev/null sh <<EOF`), atribuições, palavras reservadas e embrulhos, e lido com as aspas tiradas (`"cat"`) — é um leitor de dados conhecido (`DATA`: cat, tee, git, gh, bd, gc, jq, grep, head, tail…). Qualquer outro leitor (shell, `python3`, `ssh`, desconhecido, ou palavra que não leio) → o corpo é conferido como comando. O `$( )` de corpo com delimitador sem aspas roda sempre. Aspa que não fecha sai do texto e o resto é conferido. Comentário `#` não é lido: o que vem depois é conferido.

**Falha do próprio guarda** (exceção): se o pedido é JSON de Bash/Edit/Write/MultiEdit/NotebookEdit → bloqueia, mesmo sem a palavra "git" no texto (`g''it` não a tem); se nem é JSON → bloqueia se cita git/file_path/notebook_path, senão libera. Escape `\UFFFFFFFF` de `$'…'` é limitado a U+10FFFF (não derruba mais o guarda). O hook é `python3 -I <guarda> || exit 2`: travar, sumir o python ou o arquivo também sai com 2.

**Limites** (é trava contra engano, não sandbox).
