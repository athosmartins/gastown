## Como ligar

**1. Config do host** — `<cidade>/.gc/session-ssh.json` (ou `$GC_SSH_CONFIG`). Não existe padrão para o teto: sem `cap` o provider não abre sessão.

```json
{"default_host": "hetzner",
 "hosts": {
  "hetzner": {"ssh": "hetzner-teste", "cap": 4,
              "remote_root": "/home/runner/gt-remote/bundle", "remote_home": "/home/runner"}}}
```

| chave | obrigatória | para quê |
|---|---|---|
| `ssh` | sim | alias/destino do ssh (o mesmo `hetzner-teste` do `mbp-run.sh`; chave e usuário vêm do `~/.ssh/config`) |
| `cap` | sim, inteiro ≥ 1 | teto de sessões **deste host**, contado só no tmux do provider |
| `remote_root` | sim | o `--remote-root` que o `remote-bundle-build.py` usou; as sessões rodam sob `<remote_root>/city` e `<remote_root>/work` |
| `remote_home` | sim | o `--remote-home` do mesmo build |
| `socket` | não (`gc-remote`) | nome do socket do tmux no host (`tmux -L`): só as sessões deste provider existem nele |
| `mini_home` | não (`~`) | home do mini, para reescrever `~/…` em `remote_home` |
| `connect_timeout`, `timeout`, `start_timeout` | não (10, 25, 60 s) | prazos; o `start` leva `start_timeout` |
| `list_cache_s` | não (`10`) | segundos que uma resposta BOA do `list-running` pode ser reaproveitada (ga-it7qiq.5, ver “Cache do `list-running`”). Inteiro de 0 a 120; **0 desliga** (é o freio de mão: edite a config, vale na próxima chamada, sem janela do engine); texto, `true`/`false`, negativo, acima de 120 ou `null` recusa a config. **`0` desliga também o cache do host fora** (linha abaixo) |
| `list_down_cache_s` | não (`30`) | segundos que o FATO “o host não respondeu” (ssh 255 ou tempo esgotado) vale: dentro do prazo o `list-running` devolve erro rápido, sem ssh (ga-sml4tqk, ver “Host fora” na seção do cache). Inteiro de 0 a 60; **0 desliga só este**; texto, `true`/`false`, negativo, acima de 60 ou `null` recusa a config |
| `env_allow` | não | nomes de variável com cara de segredo que PODEM ir (ver abaixo) |
| `ssh_opts` | não | opções extras do ssh (`["-p","2222"]`) |
| `worktree_prepare` | não (`true`; `false` num host com `presence_gate`) | liga o **preparo do worktree no `start`** (identidade git + confiança da pasta, ver “Preparo do worktree”); texto no lugar de `true`/`false` é erro de configuração |
| `real_sessions_released_by` | não (ausente = só `remote-e2e-<x>`/`remote-test-<x>` abrem) | decisão EXPLÍCITA do Mayor de liberar sessão real; mesmo com ela, o `start` confere no host o guarda de clone e sai 12 se faltar (ver `hetzner-hardening.md`; em host `sleeps` o guarda mora na camada da SESSÃO, `guard_layer` abaixo) |
| `claude_account` | não (ausente = o host não segue o pool) | a sessão `claude` do host nasce na **conta atual do pool do mini** (ga-2hd02v.7.1, ver “A sessão `claude` do host nasce na conta atual do pool do mini”): `{"current_file": "/Users/athos/shared/data/claude_pool_current_account.json", "secret": "/Users/athos/.local/bin/secret"}`; `current_file` é obrigatório (caminho absoluto), `secret` é opcional (padrão `<mini_home>/.local/bin/secret`); forma errada = erro de configuração que nomeia a chave |

O host vem de `$GC_SSH_HOST` ou de `default_host`. Estado no mini: `$GC_EXEC_STATE_DIR` ou `<cidade>/.gc/runtime/session-ssh/<host>/` (`session-ssh.log`, `lock`, `meta/`).

**2. Ver o que um `start` faria, sem conectar:**

```bash
gc-session-ssh --dry-run start dog-1 < start.json     # ou GC_SSH_DRYRUN=1
```

Imprime o JSON com `command`, `work_dir`, `env`, `env_dropped`, `ignored`, o lançador, o `tmux new-session` e o `ssh` que seriam usados.

**3. Ligar no engine (só depois da janela do engine que aplica o patch).** No `city.toml`:

```toml
[session]
provider     = "hybrid"
remote_match = "-remote-"                                  # sessão cujo nome contém isto vai para o host
remote_exec  = "/Users/athos/gt/.gascity-gastown-hq/scripts/gc-session-ssh"
```

`GC_HYBRID_REMOTE_MATCH` e `GC_HYBRID_REMOTE_EXEC` valem mais que o `city.toml`. Sem `remote_exec` o híbrido segue como antes (lado remoto = K8s). **Mudar `[session] provider` é uma decisão separada desta fatia** (a cidade hoje usa o tmux padrão): o Mayor liga quando a .1.2–.1.4 estiverem prontas, porque sem `claude` no servidor uma sessão remota abre e cai.

**ATENÇÃO — trocar o provider de tmux padrão para `hybrid` derruba TODAS as sessões em execução; não é uma recarga suave (achado de 18/10, ga-2hd02v.1.6).** O engine (`cmd/gc/city_runtime.go`; as mesmas strings estão no `gc-1.1.1-engwin1016` que o supervisor roda) compara o NOME do provider a cada recarga; se mudou, roda `gracefulStopAll` em tudo o que está rodando e só então troca (`Provider changed (… → …), stopping N agent(s)…` e `Session provider swapped to hybrid.`). O supervisor não fixa `GC_SESSION` nem `GC_HYBRID_*`, então vale o `city.toml`, e o caminho nunca foi exercitado nesta cidade (0 eventos `provider.swapped`). Faça a troca dentro de uma janela do engine (que já derruba as sessões) ou numa janela própria combinada com o Mayor, com a fila do gate vazia; nunca num `gc reload --soft` solto. Se o provider novo não sobe, o engine mantém o antigo e não derruba nada.

## Operações

Cada operação é **um ssh** (ControlMaster em `~/.ssh/cm`, o mesmo do `mbp-run.sh`), com o script de shell indo pela entrada padrão. A resposta vem entre `@@GC-BEGIN@@`/`@@GC-END@@`: ruído de `.bashrc` não vira dado e resposta cortada é erro.

| operação | o que faz no host |
|---|---|
| `start` | **numa só execução**, sob `flock` no mini: confere que a sessão não existe, confere o teto, cria o diretório, grava o lançador, `tmux new-session -d`, espera 1 s e confirma que a sessão ficou de pé (senão devolve o motivo: `comando não encontrado`, `saiu com N`) |
| `stop` | mata a árvore de processos do painel, `kill-session`, apaga lançador e meta; idempotente (sessão ausente = exit 0), e **só sai 0 se, conferindo de novo, a sessão sumiu** (senão exit 1 com `continua aberta`) |
| `interrupt` | `Ctrl-C` na sessão |
| `is-running`, `process-alive`, `get-last-activity` | `true`/`false`; `process-alive` procura os nomes na árvore do painel; atividade em RFC3339. **`false` só quando o tmux do host respondeu e a sessão não está na lista**; tmux que não consegue olhar (ex.: socket sem permissão) = erro (exit 1) com o motivo, como o `list-running` e o teto do `start` (que não contam “0 sessões” nesse caso) |
| `nudge` | texto por `load-buffer`/`paste-buffer -p` + Enter (qualquer tamanho, aspas e quebras de linha) |
| `send-keys`, `peek`, `clear-scrollback` | como no tmux local |
| `list-running <prefixo>` | nomes das sessões do provider. **ssh fora = erro (exit 1), nunca lista vazia**: o engine trata erro como lista parcial e não decide nada com base num “vazio” falso. Uma resposta boa de até `list_cache_s` s (10) atrás é reaproveitada sem ssh (ver “Cache do `list-running`”); `start` e `stop` a invalidam. Com o host fora, só a 1ª chamada paga o prazo do ssh: as seguintes, por `list_down_cache_s` s (30), devolvem o mesmo erro sem ssh |
| `set-meta`, `get-meta`, `remove-meta` | ficam **no mini** (`<estado>/meta`); nada de meta vai para o servidor |
| `attach` | `ssh -t … tmux attach` |
| `check-image`, `copy-to`, `watch-startup`, `run-live` e qualquer operação desconhecida | **exit 2 (“não suportado”)**, sem abrir ssh, sem ler a entrada, sem tocar em sessão |

### Preparo do worktree no `start` (ga-2hd02v.1.5.9)

Decisão do Mayor (17/10): sessão real não abre sem identidade git e sem a pasta confiada, e não abre "meio pronta". No MESMO script do `start`, depois do teto e da existência e **antes** de criar qualquer coisa, o provider grava no host:

1. **Identidade git por worktree**: `git config --worktree user.name <sessão>` e `user.email <sessão>@gastown.invalid` (o autor dos commits da sessão remota é o nome dela). Num espelho BARE sem `extensions.worktreeConfig` o passo liga a extensão e move o `core.bare` do config compartilhado para o `config.worktree` do principal (sem isso o commit dos worktrees quebra); o `wt-add` já deixa isso certo, o passo é a rede de segurança. Depois **lê de volta**: o `user.name`/`user.email` que o git LÊ no worktree tem de ser os da sessão (outra camada de config que os sobreponha reprova).
2. **Confiança da pasta**: `projects[<work_dir>].hasTrustDialogAccepted` e `hasCompletedProjectOnboarding` em `{remote_home}/.claude.json`, troca atômica (arquivo temporário + `os.replace`), modo do arquivo mantido, lido de volta. Arquivo ausente, ilegível ou com forma que não conheço (`projects` que não é objeto): **nada é gravado** e o start falha (nunca um arquivo novo no lugar do login do claude). O claude também regrava esse arquivo, então uma gravação perdida numa corrida é possível — por isso a leitura de volta; o efeito seria a sessão parar no diálogo de confiança, que o `hetzner-proof.py e2e` reconhece e não responde.

A pasta (`work_dir` já reescrito) **tem de existir e ser um worktree git**: o start não a cria (quem cria é o `hetzner-remote-git.sh wt-add` — chamado pelo próprio provider só nos papéis de `worktree_rigs`, seção seguinte) e uma pasta comum recusa. Qualquer falha sai **exit 13** do script do host, o provider falha o `start` com `preparo da sessão <nome> recusado: <motivo>` e nada abre (nenhum lançador, nenhuma sessão, a pasta ausente não vira diretório comum). A identidade vem antes da confiança: com a identidade falhando a confiança nem é tocada.

**Padrão e exceção.** Liga em todo host, menos nos de `presence_gate` (o MBP, notebook do Athos, que tem a identidade e a confiança DELE e que o provider não escreve); `worktree_prepare` explícito vale nos dois sentidos. `--dry-run start` mostra o que gravaria em `prepare` (`git_user`, `git_email`, `trust_file`, `work_dir`; `null` se o host não prepara). Selftest: grupo `prep` (41 casos) e 12 mutantes.

### Worktree da sessão: o provider cria no `start` e recolhe no `stop` (ga-2hd02v.1.7)

Decisão do Mayor (18/10, opção 1 da ga-2hd02v.1.6): o `start` do provider não parava de falhar com exit 13 porque nada chamava o `wt-add`. Agora, **por host e por papel**, o provider cria o worktree da sessão e o recolhe quando ela para. Sem a chave, nada muda.

```json
"hetzner": {..., "worktree_rigs": {"dog": "gascity"}}
```

`worktree_rigs` é papel → rig (rig no formato do `hetzner-remote-git.sh`; forma errada recusa a configuração inteira do host, sem ssh). Ganha worktree a sessão cujo nome é `<papel>-remote-…` com o papel no mapa; `wa-worker`, `gate-reviewer` e o resto ficam como estão até alguém acrescentá-los.

* **Onde.** `<remote_home>/gt-remote/git/<rig>/wt/<sessão>` (o caminho do `wt-add`, com `GT_REMOTE_GIT` passado explícito). O `work_dir` do template (`<cidade>/.gc/agents/dogs/…`) é ignorado: não existe no host e não é o worktree. O nome da sessão vira o nome do worktree e do branch `worker/<sessão>`, então tem de casar `[a-z0-9][a-z0-9._-]{0,60}` (o formato do script); maiúscula ou `_` recusa sem abrir ssh.
* **A ordem no script do `start`** (um só ssh, sob o `flock`): já existe (exit 11) → teto (10) → **`wt-add`** → guarda de clone da sessão real (12) → preparo de identidade e confiança (13) → abre. O guarda vem **depois** do `wt-add` de propósito: o `--selfcheck` dele olha `.claude/settings*.json` DENTRO da pasta, e com a pasta ainda ausente aprovaria sem ver um `disableAllHooks` que venha no repositório (na camada `session` o `disableAllHooks: false` está ESCRITO no settings do bundle e vence o do repositório; o `--selfcheck` ainda olha a pasta). `wt-add` que falha sai **13** dizendo qual. Se o start falhar depois do `wt-add`, o `EXIT` do script recolhe o worktree que ele criou (mesma regra do `stop`); se o próprio `wt-add` morrer no meio de um worktree que ESTE start criou (checkout esparso), o start desfaz a pasta e branch novo (`wtundo`), e o retry da mesma bead não bate em “worktree incompleto”; pasta que já existia antes do start nunca é desfeita. O `wt-add` puxa o espelho antes de criar, então o start ganha um piso de 150 s (`start_timeout` menor que isso é elevado só para estas sessões, e o dry-run mostra o prazo; o engine espera 180 s em `[session] startup_timeout`). Limite: o start segura o `flock` do mini durante o `wt-add`, então outro start espera por ele — com `max_active_sessions = 1` no `dog-remote` não aparece, mas ao subir o teto de papéis com worktree isto conta.
* **O `stop`** derruba a sessão como sempre e SÓ DEPOIS tenta recolher o worktree, pelo `wt-rm`, **se nada se perde**: o worktree está limpo (`git status --porcelain` vazio **e sem nada em stderr**: um aviso do git, mesmo com rc 0, pode ser árvore que ele não leu, então mantém e o motivo diz `o git avisou ao ler o worktree`) e HEAD e o branch da sessão já estão no `origin/main` do espelho ou iguais a `origin/worker/<sessão>` / `refs/gt/published/worker/<sessão>` (a mesma definição de "publicada" do `hetzner-remote-git.sh status`). Recolhido, o branch local sai junto. **Qualquer dúvida mantém**: git que não lê o worktree ou o branch, ref ausente, `wt-rm` que falha. O resultado nunca muda o rc do `stop` (que leva um piso de prazo de 90 s, porque também roda `git status` e o `wt-rm`; só o stop de quem tem worktree; e nome que não serve de nome de worktree não o impede: derruba a sessão e só não recolhe); fica em `<estado>/<host>/events.jsonl` (`stopped.worktree` = `removed` | `kept <motivo>` | `none`) e no `session-ssh.log`. Worktree mantido não some sozinho: `hetzner-remote-git.sh status <rig>` lista o que está PENDENTE, e quem olhar e decidir descartar usa `wt-rm`.
* **Nomes que o engine gera (achado da 1.7).** Uma sessão de pool se chama `<modelo>-<cauda da bead>` (`dog-remote-gapxi4ls`) ou `<modelo>-adhoc-<10>` (`dog-remote-adhoc-0fc28155dd`) — nunca `<papel>-remote-<n>` (fonte do engine: `internal/session/names.go`, `ReadableAutoSessionName` e `GenerateAdhocExplicitName`). O `host_of` do provider lia a cauda como pedido de host e recusava. Regra agora: no meio do nome (`…-remote-<x>-…`) `<x>` é pedido de host e continua recusando host fora da config; no FIM do nome, ou `adhoc`, é a cauda do engine e vale o host padrão. Custo: `…-remote-<host>` sem número depois, com host digitado errado, cai no host padrão em vez de recusar — o MBP só abre com o nome exato do host na config.

**Identidade do atalho `bd`/`gc`.** O `remote-shim-wrapper` exige que `GC_ALIAS`, `GC_AGENT`, `GC_SESSION_NAME` e `GC_TEMPLATE` casem **todos** com o `identity_pattern` da config dele (`~/.gastown/remote-shim.json` no mini). Para as sessões remotas de pool, o valor é este (o selftest do provider lê esta linha e a prova contra os nomes reais; o que está gravado ao vivo precisa ser igual a ela):

```text
IDENTITY_PATTERN=^(remote-e2e-1|(dog|gate-reviewer|wa-worker|ps-worker|kimi-worker)-remote(-([0-9]{1,3}|adhoc-[A-Za-z0-9]{10}|[A-Za-z0-9]{3,12}))?)$
```

Casa com alias `dog-remote-1`, template `dog-remote`, sessão `dog-remote-gapxi4ls` ou `dog-remote-adhoc-…`; recusa `gastown.dog-4`, `dog-gapxi4ls`, `gastown.mayor` e as misturas (alias remoto com nome de sessão local). `kimi-worker-remote…` (ga-do1ixn.5) é o 2º papel remoto do rig gascity, o worker do teste Kimi: o padrão é global, então quem impede alias de um papel com sessão de outro (kimi × dog) é o `gate-done-remote.py`, que compara o PAPEL dos dois.

Selftest: grupo `wt` e os mutantes dele em `gc-session-ssh.selftest.sh`.

**Revisor do gate no nó (ga-2hd02v.1.9).** O padrão acima já cobre `gate-reviewer-remote-adhoc-<10>` (a sessão do template `gate-reviewer-remote`). Para o `start` abrir esse papel o host precisa de `"gate-reviewer": "gascity"` em `worktree_rigs` (sem isso o start sai 13, e o dispatcher cai no local); o dispatcher só escolhe o nó com a flag `.gc/gate-remote-reviewers.on`. Passo a passo e prova: `gate-reviewer-remote.md`.

### Sessão remota que sobe no mini: o lançador recusa (ga-pshalqe)

**O que aconteceu (27/10, lido nas beads de sessão pelo atalho do nó).** A sessão `ga-wisp-8u7ite` (template `dog-remote`, alias `dog-remote-1`, título `build ga-iqsy9c7: …`) rodou como `claude` no mini de 13:18Z até o Mayor fechá-la às 13:37Z. A bead dela tem `session_name: s-ga-wisp-8u7ite` e `sleep_capability: full` (o tmux local); as 7 sessões remotas lidas (26/10 10:03Z a 27/10 09:41Z) e a de 27/10 13:58Z (a que atendeu a ga-pshalqe) têm `session_name: dog-remote-gawisp<cauda>` e `sleep_capability: timed_only` (o provider `exec`). O alias `dog-remote-1` é o slot que o Pilot escolhe (`_pilot_node_first_dispatch`, `gc session new dog-remote --alias dog-remote-<n> --title-hint "build <bead>: …"`), não o nome da sessão. O híbrido manda a sessão ao host só quando o NOME contém o `remote_match` (`-remote-`; o patch `ga-2hd02v-hybrid-remote-exec.patch`), e `s-ga-wisp-8u7ite` não contém: o tmux do mini a abriu. A bead de sessão (criada às 13:11:33Z) é anterior ao despacho no mini da bead-fonte (13:13:08Z, comentário sem a frase "Nó Hetzner"): tudo indica uma tentativa de nó desfeita, e a sessão sobreviveu ao desfazer.

**Medido, lido, inferido.** Medido: o nome sem `-remote-` na bead de sessão e a ausência, nela, das cinco chaves de ciclo de vida (`wake_attempts`, `wait_hold`, `churn_count`, `quarantined_until`, `last_nudge_delivered_at`) que as 8 remotas lidas têm. Lido no código (o patch do híbrido e o `newHybridProvider` do engine), não visto rodar: o roteamento é `strings.Contains(nome, remote_match)`. Inferido: o engine põe `s-<bead>` em toda sessão criada com `--alias` (no código upstream, `sessionExplicitNameForNewSession` devolve vazio com alias e `Manager.Create` usa `"s-"+id`), e o engine em produção troca esse nome pelo `dog-remote-<cauda>` antes do 1º start das sessões boas; por que não trocou nesta, NÃO está provado (o código do engine em produção não está neste repositório). Para fechar: no mini, `grep -n 'ga-iqsy9c7' .gc/logs/pilot-dispatcher.log` entre 13:08Z e 13:20Z (o rc do `session new` e o aviso do desfazer) e, no código do engine, as chamadas de `ReadableAutoSessionName`.

**O que o lançador faz agora.** `scripts/claude-ctxcap-ab.sh` é o `command` do provider `claude-headless`, por onde passa TODA sessão local de claude, e o `gc-session-ssh` o troca pelo `claude` puro no host: o que chega nele é, por definição, sessão do mini. Se `GC_TEMPLATE`, `GC_AGENT` ou `GC_ALIAS` termina em `-remote` ou contém `-remote-` (os 6 templates `*-remote*` de `agents/`), ele **recusa**: uma linha `REMOTE-ONLY REFUSED template=… alias=… session=… id=…` em `<cidade>/.gc/logs/claude-lowprio.log` (`grep REMOTE-ONLY`), o motivo e os dois comandos na saída de erro, e exit 78 sem iniciar o claude. Vazio (nenhuma das três variáveis) não é recusa: o lançador está no caminho de toda sessão do pool e não pode barrar o que não sabe nomear. Desligar de propósito: `GC_REMOTE_LOCAL_GUARD=0` (um start) ou `touch <cidade>/.gc/no-remote-local-guard` (todo start novo, sem recarregar a config); o desligamento deixa uma linha `REMOTE-ONLY OVERRIDE`.

**Efeito colateral, a limpar à mão.** A sessão recusada morre ao nascer (pelo código lido, o engine tenta de novo e acaba pondo-a em quarentena); ela NÃO é "viva", então o `hetzner-idle-session-reaper` (só fecha sessão viva e sem bead) não a fecha, e o alias dela continua ocupado para o Pilot (`_pilot_node_pick_alias` só libera alias de sessão fechada ou dormindo). Fechar: `gc session close <id>` (o `id=` da linha REFUSED). Bead filha recomendada: o reaper também fechar a sessão de template remoto cujo nome não pode rotear (sem `-remote-`) e que segue aberta passado o prazo.

### O comando do `start` é o mesmo do local

O provider repassa o `command` que o engine montou (`--settings <cidade>/.gc/settings.json`, `--dangerously-skip-permissions`, `--model`, `--remote-control` quando pedido, e o `--settings {"remoteControlAtStartup":false}` das sessões headless), só reescrevendo caminhos do mini com **as mesmas regras do `remote-bundle-build.py`** (mesma fronteira de palavra): `<cidade>` → `<remote_root>/city`, `~/gt` → `<remote_root>/work`, home → `remote_home`, e `<cidade>/.gc/settings.json` → `<remote_root>/city/settings.json`, onde o bundle o instala. **Uma exceção à "como veio" (ga-2hd02v.1.5.3):** o lançador de pool do mini, `<cidade>/packs/town-deltas/assets/scripts/claude-ctxcap-ab.sh` (ou `claude-lowprio.sh`; baixam a prioridade e carregam os A/B de `--effort` e `--autocompact`, inertes sem o `.conf` na cidade), vira `claude` no host, porque o bundle não leva `<cidade>/packs` e o caminho reescrito não existe lá; a sessão remota fica fora desses A/B e do `claude-lowprio.log`. Só a PRIMEIRA palavra, e só esses dois nomes sob `<remote_root>/city/packs/town-deltas/assets/scripts/`: `…ab.sh.bak`, outra pasta de `packs/` e `env X=1 <lançador>` ficam como vieram (o lançador do host acusa `comando não encontrado`). `claude` está em `~/.local/bin`, que o `PRELUDE` põe no PATH da sessão.

**A ORDEM dos `--settings` importa (MEDIDO 17/10, claude 2.1.301 no servidor):** o engine monta o pool com o `--settings` inline PRIMEIRO e o arquivo da cidade (`<cidade>/.gc/settings.json`) por ÚLTIMO; com a ordem trocada o claude subiu sem os hooks `gc` do city (nem `gc prime` no início nem os de `UserPromptSubmit`), porque só o último `--settings` vale. O provider repassa a ordem que recebe: quem monta o pedido à mão (o `hetzner-proof.py e2e`) tem de seguir a do engine.

Se sobra `/Users/` no comando, no diretório de trabalho ou no ambiente depois da reescrita, o `start` **recusa** (uma sessão assim cairia no primeiro uso).

O **prompt de partida** também vai (campos `prompt_suffix` e `prompt_flag` do JSON do `start`, que o patch do engine acrescenta; o provider exec original não os levava, então uma sessão rodada por script ia começar sem o prompt do papel). Prompts de dezenas de KB com aspas, `$(…)` e crase chegam íntegros e nada deles é executado: o lançador temporário recebe o texto como um único argumento e se apaga ao rodar.

**Ambiente.** Só `GC_*`, `TERM`, `LANG`, `LC_*`, `TZ`. O que tem cara de segredo (`TOKEN`, `SECRET`, `PASSWORD`, `KEY`…) **não vai**, a menos que o nome esteja em `env_allow`; o `start` registra no log os nomes descartados (nunca os valores). Em particular, `GC_INSTANCE_TOKEN` não é enviado por padrão: é decisão da fatia .1.2 (shims) se o servidor precisa dele.

**O que o `start` NÃO faz** (cada item é de outra fatia ou é recusa de propósito; o que for pedido e ignorado aparece em `ignored` no dry-run e no log): `pre_start`, `session_setup*`, `session_live`, `pack_overlay_dirs`/`overlay_dir`, `copy_files` e `nudge` do JSON do start (o provider exec do engine também não entrega este último: quem entrega é o `Nudge` depois do `start`).

### A sessão `claude` do host nasce na conta atual do pool do mini (ga-2hd02v.7.1)

**Decisão do Athos (AskUserQuestion do Mayor, 20/10, citada na ga-2hd02v.7.1):** “o hetzner sempre acompanhar a conta do Mini” e “o hetzner tem que conseguir trocar sozinho entre as 5 contas”. Antes disso o `claude` do servidor usava um login fixo (uma conta só, ver `hetzner-claude-login.md`); quando essa conta estourou o limite semanal o nó parou.

**O que o `start` faz** num host com o bloco `claude_account`, para a sessão cujo comando é o `claude` (um `bash`, um `cat` ou um teste não ganham nada e não tocam no cofre):

1. lê `current` em `current_file`, o `claude_pool_current_account.json` do pool do mini (tem que ser um e-mail);
2. lê **no mini** a chave de longa duração dessa conta (`claude setup-token`, a mesma que o pool do WhatsApp usa), pelo `secret claude-oauth-token-<e-mail>`, com prazo de 15 s;
3. entrega a chave ao `claude` do host em `CLAUDE_CODE_OAUTH_TOKEN`, **como prefixo de atribuição do comando final** do lançador (`CLAUDE_CODE_OAUTH_TOKEN='…' sh -c '<comando>'`), não como `export`: só o `claude` e seus filhos a herdam (nem o vigia de presença nem o resto do lançador). O lançador vai em base64 pela **entrada padrão** do ssh, é gravado na pasta `run/` do host (modo 700) e se apaga na 2ª linha, ao começar a rodar (e nos dois caminhos de falha do `start`); é o único arquivo em que a chave existe no host. Ela não vai no argv do ssh, do lançador nem do `sh -c`, nem no log, no evento, no dry-run ou no scrollback do tmux.

**Três estados; só o primeiro abre sessão, e nenhum cai no login fixo do nó** (decisão do Athos: o login OAuth do `runner` fica só como reserva manual):

| situação | o que o `start` faz |
|---|---|
| chave lida (`secret` sai 0 e imprime `sk-ant-…` sem espaço) | abre a sessão na conta `current` |
| a conta não tem item no cofre (`secret` sai 4 com “Not found”) | recusa dizendo “sem chave cadastrada” (o cadastro é o `claude_conta_cadastrar_chave.py` do whatsapp_automation) |
| cofre fechado, `secret` que falha ou passa de 15 s, saída sem forma de chave, arquivo do pool ilegível ou `current` fora do formato de e-mail | recusa dizendo que não sabe a conta ou que a chave está ilegível |

A recusa vem **antes** de registrar a sessão, de travar e de abrir o ssh (nada sobra no host); a da chave grava o evento `refused`. O que o `secret` escreveu nunca entra na mensagem, só o código de saída. Host sem o bloco `claude_account` abre como antes. O `--dry-run` **não abre o cofre**: mostra `claude_account` com a conta atual e `"key": "não lida no dry-run"`, e um arquivo do pool ilegível entra em `would_refuse`.

**O gate mede a mesma conta.** O `hetzner-claude.py gate` mede o servidor com a MESMA chave e guarda o veredito por conta (ver `hetzner-claude-login.md`, “Seguir a conta do pool do mini (ga-2hd02v.7.1)”): quando o pool troca, a sessão nova já nasce na conta nova e o gate já mede a conta nova, sem herdar o “sem cota” da velha.

**Instalar (Mayor, depois do merge).** No `<cidade>/.gc/session-ssh.json` do **mini**, dentro do host do Hetzner, acrescentar `"claude_account": {"current_file": "/Users/athos/shared/data/claude_pool_current_account.json"}` (`secret` só se o executável não for `/Users/athos/.local/bin/secret`). O gate lê o mesmo arquivo, então uma edição liga os dois, **desde que os dois enxerguem a mesma config**: use o caminho padrão (`<cidade>/.gc/session-ssh.json`); se o engine exporta `GC_SSH_CONFIG` para o provider, quem chama o gate precisa do mesmo valor, senão o gate não vê o bloco e mede o login fixo do nó. Conferir: `gc-session-ssh --dry-run start <sessão> < start.json` mostra `claude_account.current` com o e-mail da conta atual e `key` “não lida no dry-run”; `hetzner-claude.py status --fresh --probe` mostra `account` com o mesmo e-mail e `state: ok` (o `--probe` faz a chamada de modelo, que gasta um pouco da cota dessa conta).

**Sessão viva não troca de conta sozinha.** A que já está aberta fica na conta com que nasceu; se parou no modal de limite vale a regra do pool do mini (1 Escape) ou fechar a sessão e deixar o pool abrir outra, que já nasce na conta nova.

**Limite que continua.** Quem roda `env` (ou lê o `environ` do processo, no mesmo usuário) dentro da sessão vê a chave, igual no mini: ela é uma variável de ambiente do `claude`. A chave não rotaciona, então mini e nó usam a mesma ao mesmo tempo.

**Medido × não medido.** Medido com `secret`, arquivo do pool e `claude` falsos (nada do cofre real): os três estados, o prefixo (não `export`), o vazamento (argv do ssh, saída, estado e log do mini, `ps`, scrollback e ambiente do tmux, com controle positivo) e 13 mutantes mortos; ver o grupo `acct` do `gc-session-ssh.selftest.sh`. **Não medido e não medível do servidor:** o `secret` real, o arquivo real do pool e a conta real (só no mini).

| situação | resultado |
|---|---|
| ssh fora, tempo esgotado, resposta cortada, tmux ilegível (com o ssh **tentado**) | **erro (exit 1), como antes.** Nenhuma LISTA é guardada, e o cache de listas nunca é o plano B do erro — nem o vencido, nem o de 1 s atrás. (Dentro do prazo o ssh nem é tentado: a lista boa de poucos segundos atrás sai, e essa é a defasagem aceita, abaixo.) Só “não respondeu” deixa também o FATO “host fora”, seção seguinte |
| cache vencido, de relógio que voltou (carimbo no futuro), vazio, ilegível ou com forma errada | pergunta ao host; o arquivo é reescrito |
| `lr/gen` (a geração) que não dá para ler | esta chamada **não lê nem grava** cache: pergunta ao host |
| `--dry-run` | não lê nem grava cache; imprime o que rodaria |

**Invalidação.** `start` e `stop` trocam o token de geração (`lr/gen`, troca atômica) e apagam o cache; o `start` faz isso **antes e depois** do ssh dele (o depois num `finally`: start que falhou ou ficou ambíguo também invalida), o `stop` depois. O cache só vale se a geração dentro dele for a que o chamador lê **agora**; e quem perguntou ao host só grava se a geração não mudou durante a pergunta. Resultado: uma resposta lida antes de um `start` que só chega depois dele nunca vira cache válido (coberto no grupo `lr` do selftest, com um ssh falso que segura a resposta). Falha ao trocar a geração (pasta sem escrita) NÃO derruba o `start`/`stop`: vai para o log e o guardado ainda morre sozinho em `list_cache_s` s.

**O acerto do registro de sessões nossas** (`<estado>/<host>/running/`, ver “O MBP como host”) só acontece quando o host foi perguntado: lista vinda do cache não mexe no registro.

**Custo aceito (staleness).** Até `list_cache_s` s, uma sessão que caiu por conta própria continua na lista, e uma aberta por fora do provider não aparece. Isso só pode atrasar uma decisão de vaga (sobre-contagem), e o teto do host e a existência da sessão continuam conferidos **no host, na hora**, dentro do script do `start` — o cache nunca decide o teto. Quem precisa de exatidão absoluta (o `start` já a tem) usa `list_cache_s: 0`.

**Host fora (ga-sml4tqk, 29/10).** Medido com o nó Hetzner saturado: `gc rig list` em texto levava 0,5 s, mas `gc rig list --json` passava de 120 s, com 6 cópias penduradas, cada uma esperando `gc-session-ssh list-running` → `ssh`. Causa: erro nunca era guardado, então cada uma das 16-20 chamadas em série pagava o `ConnectTimeout` (10 s) ou o `timeout` (25 s): 160-500 s. O `inflight-reclaim-guard` (20 s por consulta) ficou cego por 14+ ciclos. Conserto: o **fato** “o host não respondeu” é guardado por `list_down_cache_s` s (30 por padrão) em `<estado>/<host>/lr/down.json` = `{"gen", "ts", "msg"}`; dentro do prazo o `list-running` devolve o mesmo erro (exit 1, a mensagem diz que veio do guardado), **sem tentar o ssh**. Regras:

| situação | resultado |
|---|---|
| ssh 255 ou tempo esgotado (só estes: `Unreachable`) | erro como antes e o fato é guardado, com o carimbo de quando a falha foi **vista** (não de quando a pergunta começou: com o ssh levando 25 s para falhar, o carimbo do começo deixaria 5 s de uso) |
| resposta cortada, sem marcadores, tmux ilegível | erro de cada chamada, **nada** guardado |
| fato dentro do prazo | erro rápido sem ssh — nunca lista, nem vazia; host `sleeps` (MBP) sem sessão nossa segue só saindo da lista |
| fato vencido, de relógio que voltou, vazio, ilegível, sem `msg`/`ts` ou de outra geração | pergunta ao host (um arquivo torto nunca inventa um “fora”) |
| o host respondeu | a lista passa a ser guardada e o fato some |
| `start`, `stop` | trocam a geração e apagam o fato (a lista e o fato morrem juntos) |
| `--dry-run`, `list_cache_s: 0`, `list_down_cache_s: 0` | não usam nem gravam o fato |

Custo aceito: o host que volta continua “fora” por até `list_down_cache_s` s depois da última falha vista; o engine trata o erro como lista parcial, igual durante a queda. Com o ssh levando 1 s para falhar, 20 chamadas seguidas viram 1 ssh (antes 20), todas exit 1 (grupo `lrd` do selftest, 38 casos, 14 mutantes; contra o provider anterior 16 casos reprovam). O mesmo conserto vale para todo consumidor de `rig list`, incluindo o `gate-done`.

**Sem trava de voo único (decisão).** Chamadas simultâneas com o cache frio perguntam todas ao host. Medido (acima): as chamadas de um `rig list` são em série, então o cache corta todas menos a primeira. Uma trava para deduplicar a onda fria transformaria “host fora do ar” em N prazos de `timeout` um atrás do outro (a cada espera, a seguinte também falha), que é pior que o problema.

## Teto do host

O teto é **por host e contado à parte do teto do mini**: a contagem é `tmux -L <socket> list-sessions` do próprio host, no mesmo script que cria a sessão, sob `flock`. O teto N aceita N sessões e recusa a N+1 com `host H está no teto: N de N sessões` (exit 1); “já existe” sai como `session X already exists`, que o engine converte em `ErrSessionExists`. O teto do mini não muda.

## Quando o ssh não responde

Medido nas duas formas (porta fechada, e script com `ssh` falso que não responde): o `start` **não abre sessão**, sai com exit 1 e a mensagem diz o host e o motivo (`ssh para o host H (alvo) falhou: … Connection refused` ou `não respondeu em Ns por ssh`); a linha vai também para `<estado>/<host>/session-ssh.log`. Nada fica pela metade (nem sessão, nem lançador). `list-running`, `is-running` e `stop` também saem com erro em vez de fingir que a lista está vazia, que a sessão caiu ou que parou. O mini e o Pilot não são afetados: cada chamada é um processo curto que só depende do próprio ssh e do prazo (`timeout`).

**O ssh responde mas o tmux do host não consegue olhar** (ex.: o diretório do socket sem permissão: `error connecting to … (Permission denied)`) é o mesmo caso: erro com o motivo, em todas as operações de sessão. Só `no server running` (tmux morto) e `error connecting to … (No such file or directory)` (socket ainda não existe) contam como “nenhuma sessão”. Antes isso era tratado como “sem servidor”, e `is-running`/`process-alive` davam `false`, `list-running` dava vazio, o teto do `start` contava 0 sessões e o `stop` dizia 0 sem ter feito nada. Uma sessão **ausente** (o tmux respondeu e ela não está na lista) segue o contrato do provider exec: `stop` idempotente, `interrupt`/`nudge`/`send-keys`/`clear-scrollback`/`get-last-activity` de melhor esforço com exit 0; e o `stop` só sai 0 se, conferindo de novo, a sessão sumiu.
